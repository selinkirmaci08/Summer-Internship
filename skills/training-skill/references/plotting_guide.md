# Training Diagnostics — Plot Selection Guide

Sources: [Visualize Metrics During Training](https://machinelearningmastery.com/understand-model-behavior-during-training-by-visualizing-metrics/), [40 Interactive Plots to Analyze Your ML Pipeline](https://towardsdatascience.com/how-to-make-40-interactive-plots-to-analyze-your-machine-learning-pipeline-ee718afd7bc2/), [Useful Plots to Diagnose Your Neural Network](https://medium.com/data-science/useful-plots-to-diagnose-your-neural-network-521907fa2f45), [Plotting Training/Validation Loss Curves for the Transformer Model](https://machinelearningmastery.com/plotting-the-training-and-validation-loss-curves-for-the-transformer-model/), [Using Learning Curves to Analyse ML Model Performance](https://www.skyengine.ai/blog/using-learning-curves-to-analyse-machine-learning-model-performance/), plus cross-references into this skill's own `evaluation_metrics.md`, `hyperparameter_tuning.md`, `cross_validation.md`, `model_selection_supervised.md`, and `../../shared-references/preprocessing_and_feature_engineering.md` where a plot pairs with content already documented there.

**This table is a floor, not a ceiling** — same principle as the procedure in `SKILL.md`. If a dataset or model family surfaces a pattern that a more specific plot would explain better, generate it, save the paired CSV, and record it as an `agent_initiated_finding` the same as any other unscripted diagnostic. §9 below is a worked example of exactly that kind of addition; several rows in §1, §2, §6, §7, and §8 are themselves general-ML-practice additions beyond the five source articles, marked inline as such.

**Every plot needs a written insight, not just an image.** For each plot generated — from this table or agent-initiated — the report must state: what pattern is actually visible in this run's data, and what that implies for the next iteration or for Diagnosis's decision. A plot without that interpretation is incomplete, under the same discipline `SKILL.md` already applies to `reasoning`/`confidence` on every decision. "Numbers, not images" still applies too: every plot is paired with a CSV of its plotted values.

**Every plot also names itself, inside the image** — see `conventions/code_and_plot_conventions.md`. The figure carries its declared `name` as the title, its plot type stated in the figure ("scatter with LOESS trend", "grouped bar", "boxplot by weekday"), and its `iteration - node` provenance, using the same strings recorded in the JSON. The "type" column of every table below is that string: what this guide calls a plot is what the reader should see written on it. This matters more here than in most nodes, because training diagnostics are the plots most often pulled out of a report and compared side by side against the same plot from a different iteration, where the only thing distinguishing them is what the image itself says.

Two different things are both loosely called "learning curve" across sources — keep them distinct:
- **§3 below** = per-iteration/epoch training curve (same training set, watched across optimization steps).
- **§4 below** = score vs. training-set-size curve (varying how much data is used, same final model).
They diagnose different questions and are not interchangeable.

## 1. Core diagnostics — any task type

| Plot | Condition to generate | What it shows | How to read it | What it means for the next run |
|---|---|---|---|---|
| Feature importance (ranked bar, **grouped**) | Always (mandated in `SKILL.md` step 9) | Ranked contribution of each correlated feature *group* — never one bar per column; see `../../shared-references/feature_attribution.md`. Show each group's masked gap (joint minus sum of solo) as a second segment on its bar, so redundancy is visible rather than inferred | A small number of features dominating suggests the model is leaning on few signals; a long flat tail suggests many low-value features | Near-zero-importance features are candidates for Diagnosis to drop; a single dominant feature is worth checking for leakage (pairs with the Spearman leakage check in `SKILL.md` step 1) |
| Actual vs. Predicted (validation) | Always (mandated in `SKILL.md` step 14) | Scatter (regression) or predicted-probability overlay (classification) of validation predictions against ground truth | Points hugging the diagonal (regression) or well-separated probability mass (classification) indicate good fit; systematic curvature or banding indicates the model is missing structure | Curvature suggests a non-linear relationship the current model/features aren't capturing — a signal to Diagnosis to reconsider model family or add interaction/non-linear features |
| Residuals over time (validation) | Always (mandated in `SKILL.md` step 14) | Validation residuals plotted in chronological order | Random scatter around zero is healthy; drift, trend, or regime shifts in the residual mean indicate the model isn't capturing a temporal effect | A visible trend is the same drift concern flagged in `model_selection_timeseries.md`'s operational caveat — worth flagging to whatever stage owns monitoring/retraining, not just this iteration |
| Residuals distribution (histogram) | Always (mandated in `SKILL.md` step 14) | Distribution shape of validation residuals | Symmetric, roughly-normal-looking residuals are healthy; heavy skew or fat tails suggest the target transform (step 6b) is wrong, or outliers are being poorly fit | Skewed residuals after a log-transform was already applied is a sign the transform didn't fully fix the skew — worth trying a different transform or a loss function that tolerates it (Tweedie/Poisson — see `model_selection_supervised.md` §2) |
| Residuals vs. Predicted | Always — not yet in `SKILL.md`'s mandated list; add it | Validation residuals plotted against the model's own predicted value (not time) | A funnel/cone shape (variance growing with predicted magnitude) indicates heteroscedasticity; a flat, even band is healthy | Heteroscedasticity suggests a log-transform on the target, or a different loss function (Tweedie/Gamma deviance — see `evaluation_metrics.md` §3) rather than more tuning of the current setup |
| Train vs. validation metric comparison (grouped bar) | Always — pairs with the overfitting ratio already computed in `SKILL.md` step 8 | Primary metric's train value next to its validation value, side by side | Large visual gap corroborates a `moderate_overfit`/`severe_overfit` classification; near-equal bars corroborate `good_fit` | Makes the numeric overfitting ratio legible to Diagnosis/Planner at a glance without reading the JSON — generate whenever step 8 fires, which is every run |
| Error by feature segment | Always for at least the top 1–2 features from step 9's importance ranking; also for any categorical feature the Planner has flagged as business-critical (e.g. region, product line) | Primary metric (or mean residual) computed separately per category / per bin of a continuous feature, rather than one aggregate number | A flat line across segments means uniform performance; one segment standing out much worse means the model works well "on average" but is failing a specific slice | An aggregate metric can look fine while one important segment is quietly bad — this is often the first plot that explains *why* Diagnosis's aggregate number doesn't match a stakeholder's specific complaint |
| Feature distribution: train vs. validation | Always — cheap, and directly relevant to the `deployment_scenario` distinction already in this skill | Overlaid histograms/density curves of each key feature's distribution in train vs. validation rows | Distributions that don't overlap well indicate covariate shift between the splits, not just a modeling problem | A shift here can explain a validation-metric drop that has nothing to do with model choice or hyperparameters — worth ruling out before spending effort on step 2b/step 5 changes; also the natural first check if `deployment_scenario == "live_forecast"` and validation covers a materially different period than training |

## 2. Classification-specific

| Plot | Condition to generate | What it shows | How to read it | What it means for the next run |
|---|---|---|---|---|
| ROC curve | `task_type` is binary or multiclass classification | True positive rate vs. false positive rate across thresholds | Curve hugging the top-left corner is good discrimination; a curve near the diagonal means the model isn't beating random guessing | A weak ROC AUC with good accuracy is a class-imbalance red flag — cross-check against `evaluation_metrics.md` §2's Balanced Accuracy/PR-AUC guidance |
| Precision-Recall curve | Binary classification, **especially with class imbalance** (per `SKILL.md`'s imbalance flag in step 2b) | Precision vs. recall tradeoff across thresholds | More informative than ROC under severe imbalance — a curve that drops sharply at low recall means precision collapses quickly once you try to catch more positives | Guides the classification-threshold choice mentioned in step 7 — the "default 0.5" may not be the right operating point if this curve's shape suggests otherwise |
| Confusion matrix | Always for classification | Counts (or normalized rates) of predicted vs. actual class, all classes | Off-diagonal concentration reveals *which* classes are being confused, not just that some are | A model confusing two specific classes systematically is a feature-engineering signal (are those two classes actually distinguishable with the current `feature_subset`?) — worth flagging to Diagnosis by name, not just as an aggregate F1 drop |
| Calibration plot (reliability diagram) | Classification, pairs with the calibration computation already in `SKILL.md` step 10 | Mean predicted probability vs. observed positive rate, binned | Points on the diagonal mean probabilities are trustworthy; systematic above/below-diagonal bowing means predicted probabilities are over- or under-confident | Poor calibration matters most when downstream consumers use the probability itself (not just the class label) — flag this distinction explicitly since it changes whether the issue is even worth fixing before accepting the model |
| Cumulative gain / lift chart | Binary classification where predictions will be used to rank or target a subset (e.g. "contact the top 10% by predicted probability"), or class imbalance is already flagged | Cumulative % of actual positives captured vs. % of the population targeted, ordered by predicted probability | A curve well above the diagonal means the model concentrates positives efficiently in its top-ranked predictions; a curve close to the diagonal means ranking by this model isn't much better than random | Directly answers a different question than F1/AUC do — "if we can only act on N% of cases, how many positives do we actually catch?" — worth generating whenever that's closer to the real business question than raw classification accuracy |

## 3. Iterative-model training curves (per-iteration/epoch — see disambiguation above)

*(Sources: [Visualize Metrics During Training](https://machinelearningmastery.com/understand-model-behavior-during-training-by-visualizing-metrics/), [Useful Plots to Diagnose Your Neural Network](https://medium.com/data-science/useful-plots-to-diagnose-your-neural-network-521907fa2f45) — both neural-net-focused sources, but the underlying pattern (loss watched across training iterations, not epochs of a neural net specifically) transfers directly to gradient boosting.)*

| Plot | Condition to generate | What it shows | How to read it | What it means for the next run |
|---|---|---|---|---|
| Boosting loss curve (train vs. val, per boosting round) | `model_class` is `LGBMRegressor`/`LGBMClassifier` or `XGBRegressor`/`XGBClassifier` (both expose a per-round eval history via `eval_set`) | Train and validation loss (or the primary metric) at every boosting round | Both curves declining and flattening together = healthy; validation curve turning upward while train keeps falling = the model has passed its useful complexity for this data — classic overfitting-during-boosting signature | The round where validation loss is minimized is the correct `n_estimators`/`num_boost_round` for early stopping — if the configured value in step 5 is past that point, that's a concrete, low-risk hyperparameter fix to suggest before touching anything else |
| OOB error vs. number of trees | `model_class` is `RandomForestRegressor`/`RandomForestClassifier` | Out-of-bag error as trees are added | Error should decrease and plateau; a plateau reached well before the configured `n_estimators` means extra trees are pure compute cost with no accuracy benefit | Lets you recommend a smaller `n_estimators` without a separate validation split — cheap justification for a training-speed win |

## 4. Score vs. training-set-size (the *other* "learning curve")

*(Source: [Using Learning Curves to Analyse ML Model Performance](https://www.skyengine.ai/blog/using-learning-curves-to-analyse-machine-learning-model-performance/). Interpretation table already lives in `evaluation_metrics.md` §6 — this entry is about *when* to generate the plot, not re-deriving how to read it.)*

| Plot | Condition to generate | What it shows | How to read it | What it means for the next run |
|---|---|---|---|---|
| Learning curve (score vs. training set size) | The overfitting-ratio read in step 8 is ambiguous (borderline `mild_overfit`), or Diagnosis is specifically asking "would more data help?" | Train and validation score as training set size is progressively increased | See `evaluation_metrics.md` §6's interpretation table (high-bias vs. high-variance vs. good-fit shapes) | If both curves are still converging at the largest size tried, more training data is likely to help — a concrete, evidence-backed ask upstream rather than a guess |

## 5. Hyperparameter search diagnostics

*(Pairs with `hyperparameter_tuning.md`. Relevant only when step 5 actually ran a search — not when defaults or explicit values were used.)*

| Plot | Condition to generate | What it shows | How to read it | What it means for the next run |
|---|---|---|---|---|
| Optimization history plot | A search (grid/random/halving/Bayesian) was run in step 5 | Best-score-so-far across search trials/iterations | A curve still climbing at the trial budget's end means the search stopped too early | Justifies asking for more search budget (or a wider `n_iter`) next iteration, rather than accepting the current best as final |
| Parallel coordinate plot | A search with 3+ hyperparameters was run | Each trial as a line crossing one axis per hyperparameter, colored by score | Lines for high-scoring trials clustering on one side of an axis reveals which hyperparameter values matter; axes with no visible clustering suggest that hyperparameter barely affects performance | Narrows the next search's range around the values good trials cluster on, and lets you drop a hyperparameter (fix it at default) if it shows no clustering at all — a leaner, faster search next time |
| Slice plot (score vs. one hyperparameter, other hyperparameters marginalized) | Same condition as above, use per-hyperparameter for a cleaner single-axis read than the parallel coordinate plot gives | Score against a single hyperparameter's value, across all trials | Reveals whether the relationship is monotonic (push the range further in one direction), U-shaped (there's an interior optimum — narrow the range around it), or flat (this hyperparameter doesn't matter) | Directly informs the next search's range for that specific hyperparameter — most actionable of the three search-diagnostic plots for a quick follow-up search |

## 6. Interpretability beyond built-in importance

*(Source: [40 Interactive Plots to Analyze Your ML Pipeline](https://towardsdatascience.com/how-to-make-40-interactive-plots-to-analyze-your-machine-learning-pipeline-ee718afd7bc2/). Generate only when the condition below is met — not a default, since these are more expensive to compute than built-in `feature_importances_`.)*

| Plot | Condition to generate | What it shows | How to read it | What it means for the next run |
|---|---|---|---|---|
| SHAP bar plot | `model_family` is a tree ensemble with high-cardinality categorical features — the exact bias `model_selection_supervised.md` §6 flags for Random Forest importances (biased toward high-cardinality features) | Mean absolute SHAP value per feature — a bias-corrected alternative to `feature_importances_` | If the SHAP ranking disagrees substantially with `feature_importances_`, the built-in ranking was likely distorted by cardinality, not genuine predictive value | Report the SHAP ranking to Diagnosis as the more trustworthy one in this specific situation, and note the disagreement explicitly rather than silently picking one. **SHAP is still grouped before it is reported** — it shares the identifiability problem under correlated features, distributing credit between twins smoothly rather than arbitrarily, which reads better but is no more identifiable (`../../shared-references/feature_attribution.md` §5) |
| SHAP beeswarm plot | Diagnosis needs to know *how* a top feature affects predictions (direction, not just magnitude), not just that it's important | Per-sample SHAP values for each feature, showing spread and direction of impact | A feature with SHAP values split into two distinct clusters (rather than a smooth gradient) suggests it's acting as a proxy for a categorical effect the model hasn't been given directly | Suggests a concrete feature-engineering ask back to FE: encode whatever categorical distinction is producing the two clusters as its own feature |
| SHAP decision plot | A specific validation prediction is anomalous (a large residual flagged in §1) and Diagnosis wants to know why | Cumulative feature contributions building up to one specific prediction | Shows exactly which features pushed that one prediction away from the baseline expectation | Turns a single flagged residual into a specific, explainable cause rather than an unexplained outlier — useful for building trust in an otherwise-accepted model with a few bad predictions |
| Partial Dependence Plot (PDP) / ICE | Diagnosis wants the *shape* of one feature's effect (monotonic? a threshold? U-shaped?) rather than a single importance number, and doesn't need SHAP's per-sample detail | Model prediction as one feature is swept across its range, other features held at observed values (PDP averages across samples; ICE shows individual sample lines) | A monotonic PDP confirms the relationship matches domain expectation; a non-monotonic or threshold-like shape reveals a nonlinearity a linear model in the candidate set would miss; ICE lines that fan out (rather than staying parallel) reveal an interaction effect PDP's average would hide | A confirmed threshold effect is a concrete feature-engineering suggestion (bucket the feature, or add an explicit indicator at the threshold) rather than just "try a more complex model" — and it's built into scikit-learn (`PartialDependenceDisplay`), so no extra library dependency the way SHAP needs one |

## 7. Time-series-specific

*(Residual ACF is already mandated in `SKILL.md` step 14. Everything below is additions — pairing with `../../shared-references/preprocessing_and_feature_engineering.md` §4, `cross_validation.md`, and `model_selection_timeseries.md`. Most sources in this guide's reading list weren't time-series-focused, so several of these are general time-series-analysis practice rather than pulled from one of the five articles — marked accordingly.)*

| Plot | Condition to generate | What it shows | How to read it | What it means for the next run |
|---|---|---|---|---|
| Residual ACF (lags 1–14+) | Time-series task (already mandated) | Autocorrelation of validation residuals at increasing lags | \|r\| > 0.2 at any lag means temporal structure remains uncaptured (already the threshold `SKILL.md` step 10 uses) | A high value specifically at the seasonal lag (vs. lag-1) points Diagnosis toward "add/fix seasonal features" rather than "add more lag features" generally — worth naming which lag fired |
| Residual PACF (lags 1–14+) *(general practice, not from the reading list)* | Same trigger as residual ACF, generate alongside it — cheap, same residual series | Partial autocorrelation of validation residuals, isolating the direct effect of each lag with shorter lags' effects removed | ACF and PACF together are the standard pair for reading *which* lag structure remains: a PACF spike at a specific lag with ACF decaying gradually points to an AR-type gap; the reverse points to an MA-type gap | Turns "temporal structure remains uncaptured" into "specifically an AR(k)-shaped gap" — actionable for whether to add more autoregressive lag features (ML-as-regression path) or increase `p` (classical ARIMA path), rather than guessing which |
| Stationarity check: rolling mean/std over time *(general practice)* | Configuring or re-configuring a classical statistical model (ARIMA/SARIMA/exponential smoothing family) in step 5, before committing to a `d` (differencing) value | The raw (and, side by side, the differenced) target series with a rolling mean and rolling std overlaid | A rolling mean/std that visibly drifts over time confirms non-stationarity beyond what the ADF test's single p-value conveys; flat rolling statistics after differencing confirm the chosen `d` actually fixed it | Visual confirmation (or refutation) that the differencing order chosen actually achieved stationarity — cheaper than discovering it three steps later when the fitted ARIMA model's residuals still show trend |
| Forecast error vs. horizon step *(general practice)* | `deployment_scenario == "live_forecast"` with multi-step-ahead forecasting, or whenever Diagnosis/Planner needs to know how far ahead the model can be trusted | Primary metric (or MAE) computed separately for each forecast step (1-step-ahead, 2-step-ahead, ..., N-step-ahead) rather than one blended number | Error typically climbs with horizon; a steep early climb means the model is only reliable a few steps out, while a gentle climb means longer-horizon forecasts remain usable | Directly informs what forecast horizon the model can actually be deployed for — a single validation-set MAE can look fine while masking that step-10 forecasts are far worse than step-1, which matters a great deal for `live_forecast` |
| Model forecast vs. seasonal-naive baseline overlay *(general practice, pairs directly with the MASE/`baseline_model` already required)* | `mode == "initial"` for a time-series task — same trigger as the baseline model in `SKILL.md` step 6a | Actual, model-predicted, and seasonal-naive-baseline values all plotted together over the validation period | Periods where the model line hugs actual much more closely than the naive line visually confirm what MASE says in aggregate; periods where the model and naive lines nearly overlap show where the model isn't adding value over the trivial baseline | Makes MASE's single number legible as *where* the model earns its complexity and where it doesn't — if the model only beats naive during trend shifts but not during stable periods, that's a more specific finding than "MASE = 0.8" |
| Residuals by seasonal position (boxplot by month / day-of-week / etc.) *(general practice)* | Time-series task — complements the by-calendar-period (year/quarter) bias check already in `SKILL.md` step 10, which looks across time rather than across the seasonal cycle | Validation residuals grouped and boxplotted by their position within the seasonal cycle (e.g. one box per day-of-week for daily data with weekly seasonality) | A specific position with a consistently non-zero median residual (e.g. Mondays always over-predicted) means the seasonal feature isn't fully capturing that position's effect | More specific than "seasonal lag shows autocorrelation" in the ACF/PACF plots — names the exact day/month that needs a dedicated feature (e.g. a Monday indicator) rather than a generic seasonal term |
| Seasonal decomposition (trend/seasonal/residual) | `mode == "initial"` for a time-series task, or whenever the model family choice in step 2b is being reconsidered | The target series split into trend, seasonal, and residual components (STL, STR, or classical — see the shared reference for the choice) | A large residual component relative to trend+seasonal means there's real structure beyond what decomposition alone explains — the model needs to earn that residual variance | Confirms or challenges the step 2b assumption that "trend + seasonality" is present — if the seasonal component is negligible, a simpler model (plain ARIMA, or dropping seasonal features from the ML-as-regression path) may be justified |
| Rolling-origin backtest overlay | Time-series task, `mode == "initial"` or whenever validation strategy is being questioned | Actual vs. predicted overlaid across multiple `TimeSeriesSplit`/walk-forward folds, not just the single final validation split | Consistent accuracy across folds is reassuring; one fold performing much worse than others points to a specific period (regime change, holiday, outlier event) rather than a general model weakness | A single bad fold is a different finding than uniformly mediocre performance — report which fold and what period it corresponds to, since the fix (a calendar feature vs. a fundamentally different model) differs |

## 8. Prediction uncertainty

*(General practice — relevant whenever the model produces (or could produce) more than a point estimate.)*

| Plot | Condition to generate | What it shows | How to read it | What it means for the next run |
|---|---|---|---|---|
| Prediction interval / forecast fan chart | The model supports quantile or probabilistic output (e.g. a quantile-loss GBT objective, `BayesianRidge`, a Gaussian Process, or Pinball loss is the chosen metric — see `evaluation_metrics.md` §1) | Predicted interval (e.g. 10th–90th percentile band) alongside the point forecast and actual values | Actuals falling outside the band far more often than the interval's nominal rate (e.g. actuals outside an 80% interval more than 20% of the time) means the uncertainty estimate itself is miscalibrated, not just the point forecast | A model with a good point-forecast metric but a badly miscalibrated interval is a problem specifically for any downstream use of the interval (e.g. safety stock, confidence-based alerting) — worth reporting as a distinct finding from point-forecast accuracy |

## 9. Iteration-over-iteration tracking — worked example of an agent-initiated plot

*(Not sourced from the reading list above — this is exactly the kind of addition the floor-not-ceiling principle is meant to invite, justified by this pipeline's own structure: `mode`, `iteration`, and `history/` already exist specifically to support looping.)*

| Plot | Condition to generate | What it shows | How to read it | What it means for the next run |
|---|---|---|---|---|
| Primary metric vs. iteration number | `mode == "incremental"` and at least one prior iteration exists in `history/` | Validation primary metric plotted across all iterations so far this run | Monotonic improvement is healthy; a plateau or regression after a change signals that the most recent Diagnosis-driven modification didn't help (or hurt) | A regression after a specific change is a strong, visual argument for reverting that specific change on the next iteration rather than continuing to build on it — cheap to generate since the data already lives in `history/`, no new computation required |
