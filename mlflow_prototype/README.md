# MLflow prototype — read from `run_20260821T130000Z`, wrote nothing back

This is a throwaway demo, not a change to the pipeline. Everything here was
built by reading the existing `history/iteration_0XX_training.json` files and
`artifacts/training/*` for the 5 training iterations of
`run_20260821T130000Z` (006, 009, 010, 012, 014) — nothing in `runs/` was
modified, and nothing new was written there. All output lives in this new
`mlflow_prototype/` folder instead.

## What's in here

- `backfill.py` — the script that reads the history JSONs + artifacts and logs
  them into a fresh MLflow tracking store (`mlflow.db`). Params come from
  `output.hyperparameters.*.value`, metrics from `output.metrics.{train,validation}`
  and `output.overfitting_check.ratio`, artifacts from the plots/CSVs already
  sitting in `artifacts/training/`, and the model itself (`iteration_XXX_training_model.pkl`)
  gets registered as a proper MLflow model (that's what unlocks the model registry).
  Narrative fields your agent already writes (`mode_reasoning`, `vs_prior_iteration.note`,
  etc.) are kept as run tags rather than thrown away.
- `mlflow.db` — the resulting SQLite tracking store. One parent run
  (`run_20260821T130000Z`) with 5 nested child runs, one per training iteration.
- `shot_3_training_runs.png`, `shot_7_run_detail.png`, `shot_8_parent_run.png` —
  screenshots of what the MLflow UI shows for this data.
- `mlflow_metric_comparison.png` — a validation-MAE / overfit-ratio chart across
  the 5 iterations, generated by querying MLflow's client API
  (`mlflow.search_runs`) rather than reading the hand-written "vs_prior_iteration"
  text. This is the part that would let the diagnosis skill compare iterations
  programmatically instead of relying on prose.

## To browse it yourself, live

```
pip install mlflow
cd mlflow_prototype
mlflow ui --backend-store-uri sqlite:///mlflow.db
```

Then open http://127.0.0.1:5000 — the parent run is
`run_20260821T130000Z (bread_quantity forecast, branch 01)`, expand it to see
the 5 child iterations, click into `iteration_014_training` (the best one) to
see its full metrics/params/tags/artifacts, or select several child runs and
hit Compare for MLflow's built-in side-by-side view.

## What this does and doesn't prove

It proves the mapping works cleanly: your history JSONs already contain
exactly the params/metrics/artifacts MLflow wants, so backfilling is
mechanical, not a redesign. It does **not** prove anything about the
EDA/preprocess/feature-engineering iterations, which are much more
narrative/decision-based and don't have clean scalar metrics — those would
need a different treatment (tags + artifacts, probably not full "runs").
